  ---
  1. APPLICATION PURPOSE

  W4P is a multi-bot poker remote control system for PLO (Pot
  Limit Omaha) cash games on PokerBet (BetConstruct
  infrastructure). It allows a human operator to:

  - See all 9 controlled players' hole cards, stacks, and table
  state on a single dashboard
  - Issue action commands (Fold, Check, Call, Raise, Cashout) to
  any player via button clicks
  - Pre-queue actions (Check/Fold, Check/Call) before it's a
  player's turn
  - Monitor board cards, pot, dealer position, and street
  progression
  - Collect hand data for equity analysis

  The system operates across 3 machines: a laptop (nginx + dev),
  Cape Town EC2 (frontend proxy), and Dublin EC2 (Flask API +
  Docker player containers).

  In-memory data structures (all thread-safe via _store_lock):
  - _tables{} — table_id → canonical 9-seat table state
  - _command_queue{} — seat_token → pending command or None
  - _hero_cards{} — (table_id, seat_no) → hole cards (persists
  within hand)
  - _bot_seats{} / _seat_bots{} — bidirectional bot ↔ seat
  mapping
  - _bot_actions{} / _bot_buttons{} — available actions per bot
  - _cashout_state{} — cashout request/availability per seat
  - _hand_history[] — last 20 hands (FIFO, ASCII)

  Background threads:
  - _persist_loop() — Saves _tables to disk every 10s (atomic
  write)
  - _cleanup_loop() — Evicts stale seats (30s TTL), expires
  commands (30s), removes idle tables (5min)

  4. DATA FLOW — STEP BY STEP

  4.1 Snapshot Path (PokerBet → Remote UI)

  1. PokerBet DOM (in player's Docker container browser)
	 └─ .self-player, .single-cart-view-p, .pot-w-view-p,
  .dealer-icon-view

  2. w4p.js buildSnapshot() [every 200-600ms]
	 └─ Scrapes: hero seat, board, pot, dealer, available actions,
   button state
	 └─ Tags board with BOARD: prefix
	 └─ Hashes state → skip if unchanged (except heartbeat every
  8s)

  3. bridgeFetch() → background.js → POST /api/snapshot
	 └─ Headers: X-API-Key: trk_prod_1774368827
	 └─ Body: {table_id, bot_id, seats[], board{}, pot_zar,
  street, buttons{}}
	 └─ Response: {ok, seat_token, seat_no}

  4. Flask backend processes snapshot
	 └─ Validates API key
	 └─ Merges into _tables[table_id] (multi-hero: all 9 bots
  merged)
	 └─ Caches hero cards in _hero_cards
	 └─ Updates bot ↔ seat mapping
	 └─ Persists to state_snapshot.json every 10s

  5. Remote UI polls GET /api/table/latest [every 300ms]
	 └─ Returns merged table: 9 seats with all hero cards visible
	 └─ Diff-based render: only re-render seats whose hash changed
	 └─ Updates board, pot, street, dealer

  4.2 Command Path (Remote UI → PokerBet DOM)

  1. Operator clicks FOLD on Seat 3 in remote.html
	 └─ sendCmd(3, 'fold')

  2. POST /api/commands/queue
	 └─ {table_id, seat_no: 3, command_type: 'fold',
  remote_click_ts}
	 └─ Backend: generate seat_token, store in
  _command_queue[token]
	 └─ Response: {ok, command_id}

  3. w4p.js (in bot-leni's browser) polls GET
  /api/commands/pending?token=...
	 └─ Every 80-400ms (adaptive)
	 └─ Response: {ok, command: {type: 'fold', id, status:
  'pending'}}

  4. w4p.js handleCommand({type: 'fold'})
	 └─ clickAction('fold')
	 └─ el = document.querySelector('.control-b-view-p.fold-c')
	 └─ nativeClick(el) → mousedown → mouseup → click

  5. PokerBet processes the fold action

  6. w4p.js POST /api/commands/ack {token, command_id}
	 └─ Backend: _command_queue[token] = None
	 └─ UI sees action completed on next poll

  4.3 Raise with Amount

  1. Operator types 50.00 in slider input, clicks RAISE
  2. sendCmd(seatNo, 'raise', 50.00)
  3. Backend queues: {type: 'raise', amount: 50.00}
  4. w4p.js receives command
  5. openRaiseSlider() → clicks .control-b-view-p.raise-c
  6. Wait for slider to appear
  7. setSliderValue(50.00) → execCommand('insertText') or native
  setter
  8. confirmRaise() → click raise button again
  9. Ack command

  4.4 Pre-Action Flow

  1. Operator toggles C/F checkbox on Seat 1
  2. POST /api/commands/queue {command_type: 'check_fold'}
  3. w4p.js receives, sets _preAction = 'check_fold'
  4. When hero's turn arrives:
	 └─ runPreAction()
	 └─ If CHECK available → clickAction('check')
	 └─ Else if FOLD available → clickAction('fold')
	 └─ _preAction = null (consumed)
  5. Remote UI detects new hand → resets pre-action toggles

  6. BACKEND AND API FLOW

  Request lifecycle:
  1. HTTPS request hits nginx (port 8080, SSL)
  2. nginx matches location block:
	- Static paths → serve files directly from
  /opt/plo-engine/static/
	- /api/commands/*, /api/snapshot → proxy to 127.0.0.1:5000
  (tunnel → Dublin)
	- /api/run, /api/login, etc. → proxy to 127.0.0.1:5050
  (poker-assistant)
	- /api/* catch-all → proxy to 127.0.0.1:5000
  3. Dublin Flask processes request:
	- Rate limiting (300/min on snapshot)
	- API key validation (X-API-Key header)
	- State mutation under _store_lock
	- Response with JSON

  State persistence cycle:
  - _persist_loop() runs every 10s
  - Writes _tables to /opt/plo-equity/state_snapshot.json (atomic:
   .tmp → rename)
  - On startup: _load_state() restores from file
  - Survives Flask restart

  Cleanup cycle:
  - _cleanup_loop() runs every 10s
  - Evicts seats not seen in 30s
  - Expires unacked commands after 30s
  - Removes empty tables after 5min
  - Cleans associated hero cards, bot mappings

  ---
  7. ENGINE ↔ REMOTE SYNC MODEL

  The /engine and /remote pages are loosely coupled through the
  same backend:

  - Shared data source: Both read from _tables via
  /api/table/latest
  - Hand collector: /api/collector/latest accumulates hands for
  equity calculation
  - Equity engine: /api/run takes collected hands and computes
  matchup equities
  - No direct communication: Engine and Remote don't talk to each
  other — both independently consume the Flask API
  - Collector feed: w4p.js snapshots → backend accumulates hands →
   equity engine can consume

  9. GAPS AND MISSING PIECES

   cp, scp for each change. No CI/CD.

  3. No villain card display — By design (hero-only), but if a bot

  4. No hand history persistence — _hand_history is in-memory (max
   20 hands), lost on restart. Only state_snapshot.json persists
  table state.
  5. No tournament support — All infrastructure is cash-game PLO
  only. NLH tournament path not implemented.
  6. No multi-table view — Remote UI assumes single active table.
  If bots are at different tables, only "latest" shown.
  7. No reconnection logic in remote UI — If API goes down, the
  300ms poll silently fails (conn-dot turns red) but no auto-retry
   backoff.
  8. EIP capacity maxed — 9 players = 9 EIPs used. Need AWS limit
  increase for more players.
